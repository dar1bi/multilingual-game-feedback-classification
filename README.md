# 🎮 Multi-label Classification of Cloud-Gaming Churn Feedback

Автоматичне визначення типу технічної проблеми з текстового коментаря, який користувач
хмарного гейм-сервісу [Boosteroid](https://boosteroid.com/) залишає **в момент відписки**
від підписки. Один коментар може стосуватись кількох проблем одночасно, тому це задача
**multi-label класифікації мультимовного тексту** на 6 класів.

Увесь пайплайн — від сирих даних до порівняння семи моделей і аналізу помилок — зібраний
в одному нотбуці: [`notebooks/multilingual-game-feedback-classification.ipynb`](notebooks/multilingual-game-feedback-classification.ipynb).

Фінальна модель опублікована на HuggingFace Hub:
[**dar1bi/cloud-gaming-feedback-multilabel**](https://huggingface.co/dar1bi/cloud-gaming-feedback-multilabel).

---

## 1. Бізнес-задача та мета

Коли користувач скасовує підписку, він може залишити текстовий коментар про причину.
Компанія хоче класифікувати ці коментарі автоматично, щоб:

- **пріоритезувати інженерний беклог** за реальним обсягом скарг;
- **кількісно оцінити**, які технічні проблеми найбільше женуть відтік (churn);
- **маршрутизувати фідбек** до відповідних команд без ручного читання тисяч повідомлень.

## 2. Дані

- **Джерело:** внутрішня БД гейм-сервісу — коментарі при `SUBSCRIPTION_DELETE`.
  Дані є конфіденційними і **в репозиторії не публікуються** — див. [`data/README.md`](data/README.md).
- **Розмір:** 4 616 рядків → **3 956 після очищення**.
- **Формат:** поле `answer` містить JSON, де ключ `"other"` — текст коментаря,
  а решта ключів — проставлені мітки.
- **Мультимовність:** 70.6% англійською, далі португальська, французька, іспанська,
  українська, німецька та інші — переклад не використовувався.
- **Тексти короткі:** медіана 73 символи (13 слів), 75% коментарів — до 115 символів.
- **Multi-label:** у середньому 1.56 мітки на коментар, 65% коментарів мають рівно одну.

**Класи після очищення:**

| клас | опис | к-сть |
|---|---|---|
| `ping_latency` | мережева затримка / пінг | 2160 |
| `frames_drop` | падіння FPS, фрізи, нестабільний стрім | 1243 |
| `unable_launch` | гра або сервіс не запускається | 1097 |
| `mouse_keyboard_headset` | периферія: миша, клавіатура, гарнітура, геймпад | 747 |
| `game_bug` | баг усередині гри | 583 |
| `failed_save` | втрачений або незбережений прогрес | 339 |

**Очищення:** видалено 110 рядків з усіма 6 мітками одночасно (ймовірно тестові або
некоректно розмічені), 52 порожніх/односимвольних тексти та 498 дублікатів.

## 3. Метрика оцінювання

- **Основна — macro-F1.** Вона усереднює F1 по класах з однаковою вагою, тому рідкісні
  проблеми (`failed_save`, `game_bug`) впливають на оцінку так само, як найчастіші.
  Micro-F1 тут не підходить: у датасеті `ping_latency` зустрічається приблизно в 6 разів
  частіше за `failed_save`, тож модель могла б «їхати» на частих класах.
- **Допоміжні:** micro-F1, macro ROC-AUC, macro Average Precision (mAP).
- **Пороги** переведення ймовірностей у бінарні мітки підбираються **окремо для кожного
  класу** на validation під максимізацію F1 і без змін застосовуються до test.

## 4. Підхід та інструменти

- **Розбиття:** iterative-stratified multi-label split **70 / 15 / 15** —
  2760 / 584 / 612 прикладів (звичайна стратифікація для вектора з 6 міток не працює).
- **Представлення тексту:** три різні підходи — TF-IDF (word 1-2 грами + char_wb 2-5 грами,
  25 089 ознак), мультимовні sentence-embeddings `paraphrase-multilingual-MiniLM-L12-v2`
  (384 виміри), власна токенізація DistilBERT (`max_len=64`).
- **Дисбаланс класів:** `class_weight='balanced'` для класичних моделей,
  `pos_weight` у `BCEWithLogitsLoss` для BERT.
- **Підбір гіперпараметрів:** перебір по сітці за macro-F1 на validation для чотирьох
  моделей — `C` (LogReg), `n_estimators`/`min_samples_leaf` (RandomForest),
  `max_depth`/`learning_rate` (XGBoost), `learning_rate` (BERT).
- **Стек:** scikit-learn, XGBoost, sentence-transformers, PyTorch + HuggingFace Transformers
  (навчання на Apple MPS), OpenAI API, iterative-stratification, langdetect, matplotlib/seaborn.

## 5. Результати

Основна метрика — **macro-F1**. Усі моделі суттєво перевершують baseline.

| Модель | Параметри | Train | Val | Test | Час навч., с |
|---|---|---|---|---|---|
| **🏆 BERT (distil-mBERT)** | lr=8e-05 (grid), ep=5, maxlen=64, pos_weight | 0.808 | **0.681** | **0.620** | 862.2 |
| LLM (gpt-4o-mini) | zero-shot, temperature=0 | – | 0.660 | – | – |
| TF-IDF + RandomForest | n=300, leaf=1, balanced | 0.989 | 0.650 | – | 2.3 |
| TF-IDF + LogReg | word(1,2)+char(2,5), C=0.5, balanced | 0.818 | 0.632 | – | 0.4 |
| Embed(MiniLM) + XGBoost | n=300, depth=6, lr=0.1 | 1.000 | 0.627 | – | 32.8 |
| Embed(MiniLM) + LogReg | C=2, balanced | 0.615 | 0.623 | – | 0.0 |
| TF-IDF + LinearSVC | word+char, C=1.0, balanced | 0.934 | 0.613 | – | 0.7 |
| Baseline (most_frequent) | – | 0.118 | 0.119 | – | – |

> **Про колонку з часом:** для BERT вказано час усього перебору `learning rate` — три окремі
> тренування по 5 епох, тобто ≈ 290 с на одну конфігурацію. Для решти моделей — час
> фінального навчання без урахування підбору гіперпараметрів. Для LLM навчання немає взагалі.
> BERT рахувався на GPU (Apple MPS), решта — на CPU.

**Фінальна модель — fine-tuned DistilBERT**, обрана за найкращим результатом на validation.
Test-вибірка використовувалась один раз, уже після вибору моделі: **macro-F1 0.620**,
micro-F1 0.678, macro ROC-AUC 0.817, mAP 0.685. Порівняння всіх моделей на test свідомо
не робилось — це означало б вибір моделі під тестову вибірку.

## 6. Аналіз помилок фінальної моделі

- **Точний збіг усіх 6 міток — 45.9%** тестових коментарів. Помилки переважно часткові:
  неповний або надлишковий набір міток, а не повністю хибний прогноз. Суттєвого перекосу
  між типами помилок немає (287 зайвих міток проти 303 пропущених).
- **Якість по класах (test F1):** `ping_latency` 0.78, `unable_launch` 0.70,
  `mouse_keyboard_headset` 0.67, `frames_drop` 0.62, `game_bug` 0.49, `failed_save` 0.46.
  Найгірше розпізнаються рідкісні й семантично розмиті класи.
- **Що впливає на помилки:** передусім кількість міток у коментарі (точний збіг падає з 58%
  для однієї мітки до 0% для чотирьох-пʼяти), далі довжина тексту (найкоротші коментарі —
  найгірший результат) і мова (для представлених мов якість близька).
- **Частина «помилок» — шум розмітки:** напр. «Controle não estava respondendo» модель
  впевнено відносить до `mouse_keyboard_headset`, тоді як у даних стоїть `game_bug`.
- **Пороги дають реальний приріст:** macro-F1 на test 0.581 зі стандартним порогом 0.5 проти
  0.620 з порогами з validation, за теоретичного максимуму 0.624.

## 7. Висновки

- **Текст несе сильний сигнал:** стрибок з macro-F1 0.119 (baseline) до 0.681 підтверджує,
  що тип технічної проблеми добре визначається навіть з короткого коментаря.
- **Головний драйвер відтоку — мережева затримка:** `ping_latency` присутній у 54.6%
  коментарів і найчастіше йде в парі з `frames_drop` (849 спільних коментарів, Jaccard 0.33).
- **Стелю якості визначають дані, а не модель:** усі сім підходів укладаються в діапазон
  macro-F1 0.613–0.681. Обмежують шум розмітки, короткі тексти й семантичне перекриття класів.
- **Прості моделі майже не поступаються складним:** TF-IDF + RandomForest дає 0.650 за 2 секунди
  навчання, zero-shot LLM — 0.660 взагалі без навчання й без розміченої вибірки.
- **Обмеження:** розмітку роблять самі користувачі, тож вона шумна; класи незбалансовані;
  гіперпараметри й пороги підбирались на одній validation-вибірці; експерименти проведені для
  одного розбиття та одного seed, тому різниця в 0.01–0.02 macro-F1 лежить у межах шуму.
- **Що далі:** ручна перерозмітка підвибірки як «золотої» test, крос-валідація замість одного
  розбиття, сильніші мультимовні моделі (XLM-RoBERTa, mDeBERTa) та ансамбль BERT + TF-IDF + LLM,
  few-shot і дистиляція LLM.

## 9. Демо-застосунок

Фінальна модель загорнута у невеликий **Streamlit**-застосунок ([`app/app.py`](app/app.py)),
який класифікує довільний коментар у реальному часі.

- **Демо:** поле вводу з готовими прикладами різними мовами; результат показується двома
  блоками — передбачені проблеми людськими назвами і таблиця ймовірностей по всіх шести
  класах із порогом кожного та позначкою, спрацював він чи ні.
- **Про модель:** метрики фінальної моделі, пояснення, чому пороги різні, і чесна примітка
  про класи, які розпізнаються гірше.

Застосунок бере модель локально з `models/bert_multilabel/`, якщо вона там є, а якщо ні —
завантажує її з [HuggingFace Hub](https://huggingface.co/dar1bi/cloud-gaming-feedback-multilabel)
і кешує. Тобто демо запускається одразу після клонування репозиторію, без доступу до даних
і без перенавчання. Захардкоджених чисел у застосунку немає: пороги, класи й метрики читаються
з `inference_config.json`. Інференс займає ~60 мс на коментар на CPU.

```bash
streamlit run app/app.py     # відкриється на localhost:8501
```

Перший запуск без локальної моделі завантажить ~540 МБ ваг з Hub — далі вони беруться з кешу.

## 10. Як запустити

**Важливо:** сирих даних у репозиторії немає (див. [`data/README.md`](data/README.md)), тому
нотбук відтворюється лише за наявності доступу до вихідного датасету. Код, структура пайплайну
та всі результати прогону збережені у нотбуці й доступні для перегляду без запуску.

```bash
# 1. Залежності
pip install -r requirements.txt

# 2. Запустити нотбук
jupyter notebook notebooks/multilingual-game-feedback-classification.ipynb

# або без інтерактиву:
jupyter nbconvert --to notebook --execute --inplace notebooks/multilingual-game-feedback-classification.ipynb
```

**Примітки щодо середовища (macOS / Apple Silicon):**

- Навчання BERT використовує **MPS**; на інших платформах код автоматично переходить на CUDA
  або CPU (буде повільніше).
- На початку нотбука виставлені `TOKENIZERS_PARALLELISM=false` та `OMP_NUM_THREADS=1` — **до**
  імпорту torch і transformers, інакше воркери HuggingFace-токенізатора кладуть Jupyter-kernel.
- Розділ з LLM працює з кешу (`USE_CACHE = True`). Щоб робити реальні виклики API, постав
  `USE_CACHE = False` і поклади свій ключ у `creds.json`.
